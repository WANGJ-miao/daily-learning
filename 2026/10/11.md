MMU is necessary in operating system like Linux. But is not in MCU.
That is because on Linux, a lot of program needs running at the same time. As a programmer, I don't want to take the annoying memory allocation into consideration, so it's useful to insert such an abstracting layer that separate us apart. MMU is an implementation of the layer, which make it possible for different program to access the same imaginary address. 
However , on a MCU. Only one program is running. So this layer is unnecessary. But it does not mean a MCU directly access the physical address, which is also annoying ( strongly related to the MCU structure). Oftenly, we still access the imaginary address, mapped to the physical one.

修改之后的表达:

An MMU is important for operating systems such as Linux, but it is generally unnecessary on typical microcontrollers.

This is because Linux runs many programs concurrently. As a programmer, I don't want to worry about the physical memory layout or manually manage where each program is loaded. Therefore, it is useful to introduce an abstraction layer that separates the addresses used by programs from physical memory addresses. The MMU provides hardware support for this abstraction, allowing different processes to use the same virtual addresses while accessing different physical memory locations.

On a typical microcontroller, however, multiple tasks may run within a single firmware application, and they usually share the same address space. Therefore, a full virtual memory system is often unnecessary.

This does not mean that the CPU has no address-mapping mechanism. Microcontrollers still have a memory map that determines which address ranges correspond to RAM, Flash, and peripheral registers. However, unlike virtual memory translation, this mapping is generally fixed by the hardware rather than maintained through per-process page tables.

# FreeRTOS

## example memory allocation schemes

### heap1

Implement a very basic version of pvPortMalloc(), but does not implement pvPortFree().

Each dynamically allocated task results in two calls to pvPortmalloc(). The first allocate a task control block (TCB). The second the task's stack.

### heap2

Heap2 is superseded by heap4, which includes enhanced functionality.

Heap2 implement pvPortFree() and use best-fit algorithm to implement pvPortMalloc().

### heap3

use standard library malloc and free functions. The linker configuration defines the heap size. And the `configTOTAL_HEAP`_size constant is not used. 

### heap4

Use first-fit algorithm to malloc memory. It also combines the adjacent free blocks of memory into a single larger block, which minimize the risk of memory fragmentation.

### heap5

heap5 uses the same allocation algorithm as heap4, but unlike heap4, which is limited to allocating memory form a single array, heap5 can combine memory from multiple memory spaces.
