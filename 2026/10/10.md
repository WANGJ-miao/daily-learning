# FreeRTOS

## Data Types and Coding Style Guide

### Data Types

There are two port-specific data types: `TickType_t` and `BaseType_t`

- `TickType_t`

the number of tick interrupts that has occurred since the FreeRTOS application started is called the *tick count*

The time between two tick interrupts is called the *tick period*.

`TickType_t` is the data type used to hold the tick count value

`TickType_t` can be an unsigned 16/32/64-bit type, depending on the setting of `configTICK_TYPE_WIDTH_IN_BITS` in FreeRTOSConfig.h. The setting is architecture dependent. FreeRTOS ports will also check if the setting is valid.

- `BaseType_t`

This is always defined as the most efficient data type for the architecture

`BaseType_t` is generally used for return types that take only a verylimited range of values, and for `pdTRUE` / `pdFALSE` type Booleans.

### Variable Names

Variables are prefixed with their types: 'c' for `char`, 's' for `init16_t`(short), 'l' for `int32_t`(long), and 'x' for 'BaseType_t` and any other non-standard types (structures, task handles, queue handles, etc.).

If a variable is unsigned, it is also prefixed with a 'u'. If a variable is a pointer, it is also prefixed with a 'p'. For example, a variable of type `uint8_t` will be presixed with 'uc', and a variable of type pointer to char will be prefixed with 'pc'.

### Function Names

Functions are prefixed with both the type they return and the file they are defined within. For example:

- v**Task**PrioritySet() returns a void and is defined within tasks.c

File scope (private) functions are prefixed with 'prv'.

### Macro Names

written in upper case, and prefixed with lower case letters that indicate where the macro is defined. For example:

- configUSE_PREEMPTION defined in freeRTOSConfig.h
- taskENTER_CRITICAL defined in task.h

semaphore API is written almost entirely as a set of macros, but follows the function naming convention, rather than the macro naming convention.

- pdTRUE: 1
- pdFALSE: 0
- pdPASS: 1
- pdFAIL: 0

### using dynamic memory allocation

the general-purpose C library `malloc()` and `free()` functions may not be suitable for these reasons:

- They are not always available on small embedded systems
- Their implementation is large, taking up valuable code space
- Thsy are rarely thread-safe
- Their cost of time is fluctuating
- They suffer from fragmentation
- ...
