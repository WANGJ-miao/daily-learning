# context in Jai

context in Jai is essentially a struct, which stored some services and states.

``` c
// C-like pseudocode, not actually Jai code

struct Context {
    Allocator allocator;
    Logger logger;
    TemporaryStorage *temporary_storage;
    AssertionHandler assertion_failed;
    uint32_t thread_index;
}
```

```
allocator         : decide how to allocate for or release memory
logger            : decide where to output the log
temporary_storage : manage the temporary memory
assertion_failed  : assert what to do when failed
thread_index      : mark current thread
```

## why context?

suppose I'm writing a large program:

``` c
void A(void) {
    B();
}

void B(void) {
    C();
}

void C(void) {
    void *p = malloc(1024);
}
```

now, I want all the dynamic memory is allocated by my allocator.

``` c
void A(Allocator *a) {
    B(a);
}

void B(Allocator *a) {
    C(a);
}

void C(Allocator *a) {
    void *p = allocator_alloc(a, 1024);
}
```

The problem is A and B don't need Allocator, They change there interface just because C needs it!

if B, C ... are from the third party, you may even couldn't easily change them

In Jai, you could use context

``` jai
A :: () {
    new_context := context;
    new_context.allocator = my_allocator;
    
    push_context new_context {
        B();
    }
}

B :: () {
    C();
}

C :: () {
    p := alloc(1024);
}
```

The core thought behind it: The caller decides the executing strategy, the callee doesn't need to explicitly accept the strategy argument.

## 用户级systemd服务怎么配置？

systemd 有两套独立的unit搜索路径

|            | 系统级systemd                           | 用户级systemd         |
|------------|-----------------------------------------|-----------------------|
| 管理者     | pid 1                                   | systemd --user        |
| 配置目录   | /etc/systemd/sytem                      | ~/.config/sytemd/user |
| 操作命令   | systemctl                               | systemctl --user      |
| 默认target | 通常multi-user.target或graphical.target | 通常 default.target   |
| 运行身份   | 按照Unit配置                            | 当前用户                      |

for example:

create: ~/.config/systemd/user/hello.service

content:

```
[Uint]
Description=My service

[Service]
Type=simple
ExecStart=/usr/bin/sleep infinity

[Install]
WantedBy=default.target
```

然后启动：

systemctl --user daemon-reload
systemctl --user enable hello.service
systemctl --user start hello.service

enable 不是启动进程， 它通常根据[Install]配置创建符号链接， 例如：

~/.config/systemd/user/default.target.wants/hello.service -> ../hello.service

意思是当systemd启动default.target的时候， 应该把hello.service作为依赖一起启动

# Linux启动与systemd

我的linux电脑的启动流程[^2]

1. 初始化硬件， 寻找引导程序
2. GRUB（GRand Unified Bootloader）加载linux kernel和initramfs
3. Linux kernel 初始化内存管理， 调度器， 驱动， 其他内核子系统
4. initramfs（init ran filesystem）（初始化内存文件系统）
这上面还是内核空间， 下面进入用户空间
5. systemd（PID 1) 这是一个用来管理用户空间服务的程序， pid是1, 他会启动其他用户空间的服务

systemd可以利用 Linux 内核提供的机制，实现服务管理与资源控制, 管理用户空间的这些程序。

systemd中很重要的一种对象：units

systemd管理东西都是一个个units, units有不同的类型：target, service, slice ...

其中service一般就是我们要执行的一些程序, 例如我们在给自瞄程序配置自启动的时候, 就可以把自瞄程序包装进一个service, 然后使用systemctl enable autoaim.service来设置开机自启.
我们的电脑上跑着很多service. 例如我们需要这台电脑支持别人ssh登录进来, 那么我们电脑上就需要有一个服务启动sshd(ssh daemon)这个程序, 负责接收别人的登录请求, 通常是ssh.service(bty, sshd是服务端, ssh是客户端, 大家一般平常和ssh这个客户端打交道. sshd这个服务端程序不需要一直启动, 它可以由socket激活, 就是systemd监听端口, 在有连接请求的时候激活sshd, 这样就不需要sshd一直运行.....巴拉巴拉)
后面还会讲更多关于system的细节, 不过我现在想先讲另外一个unit: target

target很重要, 它负责管理我要启动哪些services. 例如很常见的两种target: multi-user.target, 和graphical.target. mutli-user.target 会启动一些基本的用户相关的服务, graphical.target本身包含mutli-user.target, 并且会额外启动和图像处理相关的服务. 如果你希望你的电脑充当一个服务器的角色, 一般不启动图形界面, 平常ssh登录进去操作, 有必要的时候再手动开启图形化服务, 可以考虑使用multi-user.target作为默认target.

使用命令查看默认target:  `$ systemctl get-default`
使用命令查看设置默认target: `$ systemctl set-default <YOUR TARGET NAME>` 例如: `systemctl set-default multi-user.target`

前面说道graphical.target本身包含mutli-user.target, 这意味着target是支持嵌套关系的. (其实说嵌套关系不太对, 他们之间没有那种父子嵌套关系, 更准确地说是依赖关系)
使用命令查看target的依赖关系: `systemctl list-dependencies <YOUR TARGET NAME>` 例如: `systemctl list-dependencies graphical.target`, 可以看到mutli-user.target挂载graphical.target这棵树下
使用命令: `systemctl cat multi-user.target` 查看 mutli-user.target的配置文件

```
$ systemctl cat graphical.target

# /usr/lib/systemd/system/graphical.target
#  SPDX-License-Identifier: LGPL-2.1-or-later
#
#  This file is part of systemd.
#
#  systemd is free software; you can redistribute it and/or modify it
#  under the terms of the GNU Lesser General Public License as published by
#  the Free Software Foundation; either version 2.1 of the License, or
#  (at your option) any later version.

[Unit]
Description=Graphical Interface
Documentation=man:systemd.special(7)
Requires=multi-user.target
Wants=display-manager.service
Conflicts=rescue.service rescue.target
After=multi-user.target rescue.service rescue.target display-manager.service
AllowIsolate=yes
```

[Unit] 中有很多配置项, 其中Requires指的是当决定启动A的时候, 也必须启动B, Want指的是启动A的时候, 尝试请求B, After: 指定启动顺序
啊我感觉这里存在容易发生的误解, 这里的概念并不是想当然的字面意思. 可以这样想: 这里的每一个配置选项决定systemd在特定情况下的行为, 类似一个状态机, 有时候某一个状态下的行为可能和它的配置所展现出来的字面意思不太符合我们的第一直觉. 例如: Require并不规定B启动之后才启动A, After并不根据被启动的成功与否所影响. systemd把依赖关系和启动顺序这两件事情分开了. 所以可能发生这样的情况: A requires B, 但是没有设置after或before, 所以systmed允许两者的启动程序并行(systemd倾向于并行执行, 这样更快), 这时候, 如果B启动失败, **不会**影响A, 因为这时候A的启动程序已经开始了. 如果想实现B先启动, 只有B成功启动(成功的判断条件可以通过type这个选项配置)之后才启动A, 需要同时配置Requires和After

详细的信息可以看[ww.freedesktop.org/software/systemd/man/latest/systemd.unit.html](ww.freedesktop.org/software/systemd/man/latest/systemd.unit.html "systemd.unit"), 不过我觉得一般没有人会看的, 想弄清楚就问ai吧


这里的wants很重要, 因为例如我们的程序在开机的时候自动启动, 但是又不希望自己的程序如果启动失败影响到整个用户空间的其他程序, 我们就可以把自己的service挂在multi-user.target的want下. target的want不仅仅可以在上面展示的这个配置文件中设置, 还可以放在 TARGET_NAME.target.wants/ 文件夹下, 一般会在这个目录下设置软符号链接到自己写的service, 像是这样:

```
" in  /usr/lib/systemd/system/multi-user.target.wants/
dbus.service@	 --> /usr/lib/systemd/system/dbus.service
getty.target@	 --> /usr/lib/systemd/system/getty.target
" ...
```

下面讲另一种unit类型: slice

slice 的存在目的是为了统一管理服务的资源(例如最多占用多少mem, cpu...), 注意slice区别于target是另一套分类标准, target记录的是依赖关系, slice记录的是哪些服务共同被管理, 约束.... 

例如, 如果你的user-id是1000(可以使用`$ id -u` 查看自己的user-id), 那么你启动的程序大概在user-1000.slice中被统一管理.

前面说到systemd利用 Linux 内核提供的机制实现服务管理与资源控制, slice就是对linux内核中的cgroups(Control Group)机制的一层抽象, 用来组织unit并进行管理. 可以使用 `systemd-cgls`(cgroups list) 查看cgroup

可能看到这样的层次:

```
CGroup /:
-.slice
├─user.slice
│ ├─user-1001.slice
│ │ ├─session-186.scope
│ │ └─user@1001.service …
│ │   ├─session.slice
│ │   ├─app.slice
│ │   └─init.scope
│ └─user-1000.slice
│   ├─user@1000.service …
│   │ ├─session.slice
│   │ ├─app.slice
│   │ └─init.scope
│   ├─session-3.scope
│   └─session-174.scope
├─init.scope
└─system.slice
```

注意这张图中除了slice, service, 还出现了scope. 一般来说, 后台跑的服务直接由systemd启动, 他们一般是xxx.service, 在某个slice中被集中管理. 如果是自己手动启动的某个程序, 例如在终端中启动firefox, vim... 他们没有被systemd直接启动, 但是systemd会通过scope这个unit来统一管理这些独立的进程. 如果你的user id是1000, session-id是3,  那么你手动启动的程序在cgroups这棵树中的位置应该就是user.slice->user-1000.slice->session-3.scope. (session-id 可以通过loginctl list-sessions 查看. session的概念大概指的是login session, 即登录会话, 当输入用户名和密码登录电脑的时候, 启动的就是一个登录会话)

# 用户登录与图形会话

前面说有两个常见的target, 分别叫做multi-user.target和graphical.target. 为什么叫multi-user.target? 从名字看出来启动这个target下所有的service之后, 能够支持多用户同时登录

> 是的, 多个用户同时使用这台电脑. 对于使用过服务器或者以前了解过相关概念的人可能觉得没什么, 不过对于我这个之前一直使用windows, 一直普普通通简简单单使用电脑的人来说是一件很神奇的事情. 多人同时使用, 任务并行, linux提供的抽象层次和调度系统让这件事很自然地被实现了

linux中提供很多虚拟终端(vt, virtual terminal), 例如/dev/tty1, /dev/tty2 .... 一般最多63个, vt就是模拟以前真实的串口通信的终端设备的一个软件实例, 它直接控制显示器的输出

如果身边有可以使用的 linux 电脑, 可以使用 Ctrl-Alt-F3(3到6之间的数字都可以, 至于为什么是这几个数字后面会解释), 进入一个虚拟终端, 然后你会看到一个闪动的光标, 如果屏幕上出现了 ... login: 这说明你的电脑中agetty(负责决定显示什么内容. BDW, vt负责显示和使用line discipline显示输入的字符)和login(读取密码, 验证, 启动用户的shell)这两个用户空间的程序已经正常启动了. 如果验证通过, login程序就会启动一个shell, 接下来你可以通过这个shell和你的电脑进行交互, 例如启动程序

agetty@tty[n].service负责启动agetty程序(n是一个数字, 这里的@表示模板, 就是说有一个叫agetty@tty.service的模板服务, 可以在它的基础上存在agetty@tty[n].service这些服务). agetty会执行login(使用exec, 而不是fork的方式, 所以在进程树中看不到agetty(可以使用`pstree -p`看进程树), 而是直接看到systemd->login->bash->...[^3])

agetty@1.service 在 mutli-user.target 之下依赖关系是 default.targt->multi-user.target->agetty.target->agetty@tty1.target . 注意, 这里没有 agetty@tty2.service 及以后的 service, 所以2及以后的虚拟终端中的 agetty 程序不是默认启动的, 不过可以被 systmd-login 这个程序通过启动(这个程序是 systemd fork 出来的, 当内核切换vt[n], systemd-logind会检查NAutoVTs的配置, 如果n在配置之内, 就会请求启动autovt@tty[n].service(通常是getty@tty[n].service的别名), 然后systemd启动agetty, 显示login:
NAutoVTs的配置可以在/etc/systemd/login.conf中查看. 一般默认配置是1-6有这种trigger的机制(可以自己改配置), 所以上面让大家在Ctrl-Alt-F[n] 在6以下)

目前还没有涉及任何的图形界面, 上面提到的login程序是终端登录的方式. 但是一般大家使用的都是图形界面登录方式, 例如最常见的一种实现方案是GDM, ubuntu和fedora发行版用的都是GDM. 和getty一样, GDM也由systemd管理, 它在display-manager.service中, **这个服务在graphical.target中**, 所以如果你想通过图形界面登录, 最好把graphical.target设置为默认target. 当然你也可以手动启动这个服务, 这样就会弹出一个图形登录窗口, 选择想要启动的桌面环境, 输入账号密码.

如果选择graphical.target作为默认target, GDM会占用tty1作为登录页面, 这样你登录进去之后启动的桌面环境大概在tty2. 这样就解释了前面留下的一个问题(为什么建议你们尝试虚拟终端的时候使用切换到3-6, 而不是1, 2, 以及6以后)

# 和战队小电脑管理相关

和战队小电脑最相关的东西我觉得大概有两个:
一个是之前每次使用momachine远程连接的时候都需要插上一个诱骗器, 之前也没弄清楚为什么, 并且感觉很麻烦.
另一个是和小店脑自瞄以及导航决策的自启动相关. 到底应该怎么设置这些程序的自启动, 原来的方案合理么?

## 首先第一个问题: 远程连接 

*下面使用nomachine这个特定的软件代指一般远程桌面软件*

远程桌面有两种工作模式: 
一种是共享物理桌面, 大概就是小店脑本身已经创建了一个session, 并且启用了一个桌面环境, nomachine可以直接拿到compositor生成的桌面画面(之后有时间再补充关于图形桌面生成的内容), 然后运行在小店脑上的nomachine服务端把画面内容经过编码后(可能是用H.264, VP8, MGPEG等方式)发给运行在大家自己电脑上的nomachine客户端上, 显示出来[^5].这种方案需要诱骗器(诱骗器的功能是告诉显卡驱动存在显示器, 并且告诉显卡驱动我这个"显示器"支持多少分辨率, 多少刷新率.... 显卡不仅仅负责计算, 同时负责把视频画面发出来, 所以大家应该可以直接看到显卡上出来的各种接口), 如果显卡驱动不支持headless输出(headless指的就是没有显示器), 那Xorg(x11协议的服务端软件实现)就会启动失败, 不会有正常画面
第二种工作模式是创建独立的虚拟桌面, 例如如果使用xrdp + xorgxrdp + XFCE(啊我这里又多了好多新可以说的东西, 后面有时间一起整理), 即使小电脑本地没有启动本地图形桌面, 远程连接也可以创建一套新的图形session. 这种方式不需要物理的hdmi显示器, 而是通过xorgxrdp使用虚拟显示后端, 分辨率等信息可以软件指定, 因此这种方式不需要诱骗器(HDMI Dummy Plug). 不过针对GNOME桌面, GNOME 46 之后引入了远程登录的支持, 因此Ubuntu24.04才开始提供Remote Login功能, (Ubutnu22.04上适用的是GNOME 42. 不太好只升级gnome而不升级ubuntu, 依赖比较复杂(._.`)  ), 但是我们可以选择使用xfce桌面(如果大家不嫌弃它太丑), x11协议虽然很老, 但是很成熟

## 第二个问题: 关于自启动

先来看一下`sp_vision_25`中给的方案: 

```
注册自启：

确保已安装screen:

sudo apt install screen

创建.desktop文件:

mkdir ~/.config/autostart/
touch ~/.config/autostart/sp_vision.desktop

在该文件中写入:

[Desktop Entry]
Type=Application
Exec=/home/rm/Desktop/sp_vision_25/autostart.sh
Name=sp_vision

注: Exec必须为绝对路径.
确保autostart.sh有可执行权限:

chmod +x autostart.sh
```

这个是什么原理呢? XDG(cross-desktop group, 这是一个关于桌面的规定, x11协议和wayland协议都在遵守)规定, 桌面环境在用户登录并启动图形会话的时候, 读取~/.config/autostart/下的.desktop文件并启动相应的程序. 这些程序在对应用户的桌面会话启动过程中运行, 最终可能交给用户级systemd管理(是的, systemd有系统级和用户级, 用户级是systemd --user), 因此, 只要用户登录失败, 或机器没有启动图形桌面, 或意外退出图形桌面, 这些程序大概就会终止. 所以这套流程依赖图形桌面, 但是对于自瞄, 导航这样的程序, 我们应该让他们独立于特定的用户有没有进入桌面. 同时.desktop文件告诉桌面环境启动一个程序, 也只是告诉它尝试启动这个程序, 没有定义如果这个程序启动失败怎么处理, 是否要重新启动, 这个程序是不是需要等某些服务已经可以使用之后再启动, 例如usb设备可用了么, ros2通信服务启动了么...

更加合理的方案是把这些程序注册成systemd系统级服务, 可以创建`/etc/systemd/system/sp_vision.service`, 写入:

```
[Unit]
Description=autoaim

[Service]
Type=simple
User=nvidia
WorkingDirectory=/home/nvidia/project/autoaim
ExecStart=/home/nvidia/project/autoaim/start.sh
Restart=on-failure
RestartSec=3

[Install]
WantedBy=multi-user.target
```

这里规定了这个服务执行start.sh这个脚本, 如果失败了就隔三秒重启, 然后挂在multi-user.target之下(还可以加上别的启动顺序条件, 或者在脚本中加也可以), 所以程序启动的时候就会启动这个服务. 和用户有没有登录, 有没有成功启动桌面都没有关系.

然后就可以使用各种systemd提供的功能来管理这个服务了(可以使用systemctl, systemctl可看作systmd的client, 用来控制和查询systemd)
例如:

``` bash
# 查看服务状态
systemctl status autoaim.service

# 查看日志
journalctl -u autoaim.service -b

# 实时查看日志
journalctl -u autoaim.service -f

# 重启业务程序
sudo systemctl restart autoaim.service

# ...
```

既然以前这些程序依赖用户登录和图形桌面的启动, 那为什么之前小电脑依然可以上电就开始跑我们的程序呢? 这时因为之前设置了用户的自动登录, 在`/etc/gdm3/custom.conf`中可以看到:

```
[daemon]
AutomaticLoginEnable=true
AutomaticLogin=nvidia
```

所以之前的流程就是: 上电, gdm3提供自动登录, 登录nvidia这个用户, 并且启动gnome桌面环境, gnome-session-binary(GNOME的会话管理程序)扫描到.desktop, 启动程序. 这样也...能跑, 不过引入了不必要的依赖
