# systemd

## central concept: unit

systemd organize its work using objects called units.

My computer contains a collection of manageable units, tith relationships between them.

there are several unit types:

| Unit type    | Purpose                                  | Example                   |
|--------------|------------------------------------------|---------------------------|
| `.service`   | Manages services                         | `ssh.service`             |
| `.socket`    | Manages sockets                          | `systemd-journald.socket` |
| `.target`    | Groups units into synchronization goals  | `multi-user.target`       |
| `.mount`     | Manages filesystem mounts                | `home.mount`              |
| `.automount` | Automounts filesystems                   | `home.automount`          |
| `.timer`     | Triggers scheduled actions               | `apt-daily.timer`         |
| `.path`      | Watches filesystem paths                 | `cups.path`               |
| `.device`    | Represents devices                       | `dev-sda.device`          |
| `.slice`     | Groups processes for resource management | `user.slice`              |
| `.scope`     | Groups externally created processes      | `session-3.scope`         |

## service units

a service units manages a service or a daemon

examine a service's configuration: `systemctl cat ssh.service`

``` bash
wangj@thinkpad:~$ systemctl cat ssh.service
# /usr/lib/systemd/system/ssh.service
[Unit]
Description=OpenBSD Secure Shell server
Documentation=man:sshd(8) man:sshd_config(5)
After=network.target auditd.service
ConditionPathExists=!/etc/ssh/sshd_not_to_be_run

[Service]
EnvironmentFile=-/etc/default/ssh
ExecStartPre=/usr/sbin/sshd -t
ExecStart=/usr/sbin/sshd -D $SSHD_OPTS
ExecReload=/usr/sbin/sshd -t
ExecReload=/bin/kill -HUP $MAINPID
KillMode=process
Restart=on-failure
RestartPreventExitStatus=255
Type=notify
RuntimeDirectory=sshd
RuntimeDirectoryMode=0755

[Install]
WantedBy=multi-user.target
Alias=sshd.service
```

[unit] : relationships and metadata
[service] : how to manage the program
[install] : how to enable it?

**install** : this is really important. when I've written wantedby multi-user.target and enable this unit, systemd typically creates a sysmbolic link under `/etc/systemd/system/multi-user.target.wants/`

``` bash
wangj@thinkpad:multi-user.target.wants$ file ssh.service
ssh.service: symbolic link to /usr/lib/systemd/system/ssh.service
```

## target unit

a target is synchronization point(目标), that groups units through dependencies.

Unlike a service, a target doesn't normally have its own executable program.

a simplified boot progression looks like: systemd->sysinit.target->basic.target->multi-user.target->graphical.target

### multi-user.target

whis normally provides a system ready for multiple users, including services and login facilities. I does not reauire a graphical desktop.

### graphical.target

This builds on the multi-user environment and normally adds a display manager.

A display manager might be: gdm, sddm, lightdm

even when the default target is multi-user.target, I can manually start an X11 session.

## dependencies : how sysmd orgahnizes startup

### Wants and Requires

Wants=

when activating this unit, also try to activate `network.target`, but when the dependendy fails, the unit can still start.

Requires=

this establishes a stringer dependency. If dependencies failed, the dependent unit will not start

### after and before

``` 
[Unit]
Requires=database.service
After=database.service
```

this means start the required database service, wait for its startup job to complete, then start this service

all these dependencies come to a graph, instead of a traditional sequential startup script.

## systemd has two important organizational structures

one is unit dependencies, which answers which units need to be activated, and in what order?

the other is control groups(cgroups), which answers which processes belong together, and how should their resources be managed?

### slice

a slice is a group of units managed toghther for resource control.

for example:

system.slice typically contains system services, user.slice contains processes associated with users. And each user normally receives a slice such as: user-1000.slice

why need to group?

because systemd can apply resource limits to a whole group. for example, a slice can control how cpu time or memory is destributed among the processes inside it. the kernel enforces these controls through cgroups; systemd configures and manages them.

### scope

a scope is used to manage processes that were created externally rather than launched directly by the systemd service manager.

for example: session-3.scope may represent a login session.

## compare pstree and systemd-cgls

`pstree -p` displays the parent-child process tree.

`systemd-cgls` displays cgroup hierarchy

| `pstree`                                           | `systemd-cgls`                                     |
|----------------------------------------------------|----------------------------------------------------|
| Shows process ancestry                             | Shows cgroup membership                            |
| Based on parent-child relationships                | Based on resource-control groupings                |
| Process relationships are maintained by the kernel | Groups are managed by systemd using kernel cgroups |
| Answers: Who created this process?                 | Answers: Which group manages this process?         |

## how systemd manage tty login?

``` plain_text
systemd (PID 1)
   │
   ├── systemd-logind.service
   │
   ├── getty@tty3.service
   │       │
   │       ▼
   │     agetty
   │       │
   │       ▼
   │      login
   │       │
   │       ▼
   │      bash
   │
   └── user@1000.service
           │
           ▼
       systemd --user
```

getty@tty3.service @ means this is a template unit.

what happens when pressing C-M-F3?

1. The keyboard event requests a switch to virtual terminal 3.
2. The kernel's virtual terminal facilities perform the switch
3. If necessary, systemd-logind coordinates the activation of a login service for that terminal.
4. agetty presents a login prompt.
5. after authentication, the shell starts?

The kernel handles virtual terminals. systemd manages the login service.

## systemd refers to a larger sofrware suite rather than a single program

| Component           | Responsibility                               |
|---------------------|----------------------------------------------|
| `systemd`           | System and service management                |
| `systemctl`         | Command-line interface for controlling units |
| `systemd-logind`    | Manages login sessions and seats             |
| `systemd-journald`  | Collects system logs                         |
| `systemd-udevd`     | Handles device events                        |
| `systemd-networkd`  | Network configuration, when used             |
| `systemd-resolved`  | DNS resolution, when used                    |
| `systemd-timedated` | Provides time/date configuration interface   |

but not all components are active on every Linux installation. For example, Ubuntu systems may use NetworkManager instead of systemd-networkd for network management

### systemctl

``` plain_text
You
 │
 ▼
systemctl
 │
 │  IPC / D-Bus communication
 ▼
systemd (PID 1)
 │
 ▼
Unit management
 │
 ▼
Kernel operations
```

systemctl is a client program. It sends requests to the systemd manager.

### journalctl

journalctl is client program to systemd-journald.

systemd-journald collects logs generated by system services, the kernel, and other sources.

``` bash
journalctl -u ssh.service
```

shows log entries associated with the unit: ssh.service

``` bash
journalctl -k
```

-k / --dmesg show kernel messages

``` bash
journalctl -f
```

-f to follow the logs in real time.

## where does systemd store its configuration?

unlike kernel, which has many runtime interfaces undrer /proc and /sys, systemd uses unit configuraion filesto describe its management policies.

``` plain_text

/run/systemd/system/
/usr/lib/systemd/system/
```

# what is shell

a shell is a program that interprets commands and provides an interface for interacting with the operating system.

common unix shells include:

| Shell  | Description                      |
|--------|----------------------------------|
| `sh`   | Traditional Unix shell interface |
| `bash` | Bourne Again Shell               |
| `zsh`  | Z Shell                          |
| `fish` | Friendly Interactive Shell       |
| `dash` | Lightweight POSIX shell          |

## difference between terminal emulator and shell

terminal emulator : A program that provides an interface for text input and output.

shell: A program that reads, interprets, and executes commands.


# process and thread

process: An abstraction that owns resources, including an address space, file descriptors, and other operating-system state

thread: An execution stream with its own program counter, register, and stack.

a thread can contain multiple threads.

a useful mental model:

- process = resource container
- thread = execution unit

## why 'kernel threads' rather than 'kernel processes'?

Because kernel threads generally do not own independent userspace process resources
