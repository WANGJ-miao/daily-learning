# WebRTC
3个基本逻辑角色
Peer A: 想发送视频
Peer B: 想接收视频
Signaling Server: 信令服务器, 可以是WebSocket server, HTTP server, Socket.IO, 自己写的tcp服务
Signaling server 负责在A和B建立P2P连接之前, 先帮助它们传话
包括sdp offer, sdp answer, ice candidate, user id, home number, request
WebRTC并不要求通过什么方式实现信令交流. 甚至可以手动把程序A输出的sdp赋值剪贴给程序B. 选择使用信令服务器是为了更方便
流程:
1. B向A发送请求
2. 两者建立PeerConnection
3. 假设A主动发起协商, 它就是offerer, 它生成sdp, 表示自己的通信能力和本次通信的内容
4. A通过信令服务器, 把这个sdp发给B
5. B收到offer, setRemoteDescription
6. B根据offer, 生成answer, 然后通过websocket发出去
7. A收到answer, setRemoteDescription
8. 开始ICE candidate 收集
    ICE candidate 通常有3种类型:
    1. host candidate 本机地址, 例如: 192.168.1.137:6000 10.0.0.5:50000 像是局域网就可以直接使用这个
    2. srflx candidate 如果在NAT之后, 可以通过STUN Server询问自己在公网环境中看起来是什么IP:port
    3. relay candidate 如果NAT太严格, P2P打洞失败, 会走这一个方法. A -> TURN server -> B
    例如: TURN: 54.x.x.x:50000, 以后媒体就通过TURN 服务器转发

# sdp
``` plain text
v=0
o=- 4611731400430051336 2 IN IP4 127.0.0.1
s=-
t=0 0

a=group:BUNDLE 0
a=msid-semantic: WMS

m=video 9 UDP/TLS/RTP/SAVPF 96
c=IN IP4 0.0.0.0

a=mid:0
a=sendonly

a=rtcp-mux
a=rtcp-rsize

a=ice-ufrag:abcD
a=ice-pwd:abcdefghijklmnopqrstuv
a=ice-options:trickle

a=fingerprint:sha-256 AA:BB:CC:DD:...
a=setup:actpass

a=rtpmap:96 H264/90000
a=fmtp:96 packetization-mode=1;profile-level-id=42e01f

a=ssrc:42 cname:video-send
```
1. v version 目前都是0
2. o origin 描述这个sdp来自哪里
``` plain text
o=-     4611731400430051336     2       IN      IP4         127.0.0.1
username, session id,       session version, network-type,  address
```
这里-表示是无意义的用户名,  IN 表示Internet, 这里的address没有实际意义, 真正的地址由ice candidate决定
s: session name 但是webrtc根本不关心, 一般就是-
t: start-time end-time 表示这个session从什么时候开始, 什么时候结束. 但是也没意义, webrtc不使用这个控制声明周期
a: attribute 属性, 这里是真正有意义的信息. 
mid: media id
m: media 表示一条media description
