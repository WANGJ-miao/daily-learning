# WebRTC
浏览器原生支持的一种实时音视频传输系统, 它不是一个库, 而是一整套机制, 浏览器和远端怎么连接?各种数据怎么传输?丢包怎么处理?浏览器怎么解码并播放?...
WebRTC=让浏览器能够接收实时视频流并挂到\<video\>上播放
**数据流**
相机原始帧->H264编码器->WebRTC发送端->网络->浏览器WebRTC接收端->浏览器解码器->\<video\>显示
但是不是发送裸的字节这么简单, 在发送之前, 需要和浏览器"协商", 有三种东西
- offer
- answer
- ICE
offer/answer解决"怎么说话", ICE解决"怎么找到对方并连上"
浏览器需要知道这些信息:
- 对方发不发视频
- 发几路视频
- 用什么编码格式
- RTP包怎么组织
- SSRC, payload type, rtcp feedback这些参数是什么
- 是否要回传网络控制信息
- 加密参数是什么
这轮协商的文本描述, 就是SDP
offer/answer就是两份SDP(session description protocol)
offer: 浏览器向c++发送, 格式提议
answer: c++端向浏览器发送, 自己能做到什么地步, 应答方最后的结果
ICE(Interactive Connectivity Establishment): 怎么找到对方, WebRTC的探路机制. 双方交换能访问到的地址, 然后逐个尝试, 这些候选地址就叫做ICE candidates
ICE candidates的来源:
- 本机局域网地址
  - 比如 192.168.x.x
- NAT 映射出来的公网地址
  - 通常借助 STUN 知道
- 中继地址
  - 借助 TURN
STUN = Session Traversal Utilities for NAT
TURN = Traversal Using Relays around NAT
整个过程:
1. 浏览器创建 RTCPeerConnection
2. 浏览器生成 offer
3. 浏览器把 offer 通过你的 WebSocket 发给 Node
4. Node 再转给 C++ 端
5. C++ 端创建自己的 WebRTC PeerConnection
6. C++ 用这个 offer 生成 answer
7. C++ 把 answer 通过 Node 转回浏览器
8. 双方继续交换 ICE candidates
9. ICE 连通后，媒体通道建立
10. C++ 开始发 H264 视频
11. 浏览器收到视频轨，挂到 <video>
